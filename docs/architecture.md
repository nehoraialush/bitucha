# אפיון טכני — מערכת ליבה לביטוח חיות מחמד

סטטוס: שלב ראשון — תכנון. מסמך זה אינו מעיד שמודולים עסקיים מומשו.
יעד: סימולציה תפעולית מקומית עם נתונים בדויים בלבד. כל סליקה וחתימה מדומות.

## מקורות, הנחות וכללים

המקור לדרישות המוצר הוא מסמך הבקשה שסופק בפרויקט. לא אומתו בשלב זה מקורות ישראליים חיצוניים או הוראות דין. אין לקבע כלל רגולטורי על סמך המסמך. לפני שימוש אמיתי יש להשלים סקירה משפטית ואבטחת מידע.

כללי גיל כניסה, גזעים, אכשרה, החרגות, החזר ביטול, השתתפות עצמית ומגבלות חיתום הם הגדרות סימולציה הניתנות להגדרה בגרסת מוצר. סטטוס אימות לכל כלל: `SIMULATION`, `ASSUMPTION`, `VERIFIED`. כלל מאומת מחייב מקור, תאריך בדיקה ומאשר. אין לייחס תוקף משפטי לחתימה המדומה.

מקורות להמשך אימות: רשות שוק ההון, ביטוח וחיסכון ב־gov.il; תנאי פוליסה שפורסמו בידי המבטח הרלוונטי; הרשות להגנת הפרטיות. יש לתעד מסמך מדויק, גרסה וסעיף, ולא להסיק תנאים מחומר שיווקי.

## ארכיטקטורה

מונולית מודולרי: React + TypeScript, NestJS + REST/OpenAPI, PostgreSQL, Prisma. לכל מודול שכבת controller, שירותי application, domain וגישה לנתונים. מנועי חישוב הם פונקציות נפרדות וניתנות לבדיקה. שירותים משתמשים בטרנזקציות לכתיבה. controllers אינם מחשבים סכומים.

מבנה הפרויקט המתוכנן:

- `apps/web`: ממשק עברית ו־RTL, Tailwind ו־shadcn/ui, טפסים ותיק לקוח.
- `apps/api`: אימות, הרשאות, מודולים ושירותי תהליכים.
- `packages/domain`: כסף, זמן, כללים, מכונות מצבים וחישובים.
- `packages/contracts`: טיפוסי API וולידציה משותפים, ללא תלות ב־Prisma בממשק.
- `prisma`: schema, מיגרציות ו־seed.
- `tests`: בדיקות אינטגרציה ו־Playwright.
- `infra`: Dockerfiles ותצורת Docker Compose להפעלה גם ב־Windows.

React לא ניגש ישירות למסד הנתונים. PostgreSQL הוא מקור האמת; דוחות ומסמכים נגזרים ממנו. אין שירותי סליקה חיצוניים בשלב הראשון. PostgreSQL ושרת API מספיקים למסלול הליבה; worker למסמכים ואירועים נוסף כאשר יש לו תהליך ממשי.

## ישויות וקשרים

לכל רשומה UUID פנימי, מספר תפעולי לפי sequence במידת הצורך, `createdAt`, `updatedAt` וגרסת concurrency. כספים נשמרים באגורות שלמות ב־BIGINT; אין חישוב כסף ב־floating point. המטבע ILS. תאריכי אירוע ותקופת ביטוח הם DATE; זמני ביקורת UTC, הצגה לפי Asia/Jerusalem. תקופות הן `[תחילה, סוף)`.

| תחום | ישויות | קשרים ואילוצים |
|---|---|---|
| זהות | Employee, Role, Permission, EmployeeRole, RolePermission, Session | כתובת כניסה ייחודית; תפקידים אינם מחליפים בדיקת פעולה |
| לקוחות | Customer, Contact, Address, CustomerRepresentative, CustomerNote | מזהה בדוי בלבד ב־seed; הפניות מקושרות לתיק |
| בעלי חיים | Pet, Breed, MedicalCondition, PetMedication, MedicalRecord, PetDocument | בעלים תקף; שבב לא ריק ייחודי; היסטוריית בעלות מפורשת |
| מוצרים | Product, ProductVersion, CoverageDefinition, ProductCoverage, RuleVersion | גרסה שפורסמה בלתי ניתנת לשינוי; גרסאות טיוטה נפרדות |
| הצטרפות | Application, QuestionnaireAnswer, HealthDeclaration, Quote, UnderwritingCase, UnderwritingDecision | הצעה שומרת snapshot של תנאים וחישוב; החלטות לא נדרסות |
| פוליסות | Policy, PolicyVersion, PolicyPeriod, PolicyCoverage, Exclusion, Endorsement | לקוח ובעל חיים עקביים; מוצר וגרסה מפורשים; מניעת תקופות כיסוי חופפות אסורות |
| תביעות | Claim, ClaimLine, ClaimDocument, Assessment, ClaimDecision, Appeal | כל שורה בעלת אירוע, כיסוי וחישוב; החלטה היא גרסה חדשה |
| יתרות | CoverageAccount, CoverageReservation, CoverageMovement | חשבון לפי תקופה וכיסוי; unique על אירוע המקור; יתרה אינה שלילית |
| כספים | Charge, Collection, Allocation, Credit, Refund, PaymentOrder, PaymentExecution, LedgerEntry | לכל ביצוע מפתח idempotency; שורות ספר חשבונות מאוזנות |
| מסמכים | Document, DocumentVersion, TemplateVersion, SimulatedSignature | snapshot נתונים, hash, תבנית, גרסה וזמן; קובץ מחוץ לטבלאות גדולות |
| שירות | ServiceCase, ServiceEvent, Task, Assignment | שיוך לקוח וישות עסקית; העברה ותיעוד טיפול |
| בקרה | AuditEvent, IdempotencyRecord, OutboxEvent | אותו commit כמו השינוי; מזהה תהליך; ללא סיסמאות או טוקנים בביקורת |

מחיקה קשיחה של פוליסה, תביעה, מסמך או תנועה כספית אינה פעולה תפעולית. תיקון כספי הוא תנועת נגד. נתוני לקוח רגישים מוגבלים לפי הרשאה; מדיניות שמירה ואנונימיזציה טעונה אימות לפני שימוש אמיתי.

## מצבים ותנאי מעבר

פוליסה: `DRAFT → QUOTED → UNDERWRITING_PENDING → PAYMENT_PENDING → ACTIVE`. חיתום אוטומטי יכול לעבור ישירות מ־QUOTED ל־PAYMENT_PENDING. הפעלה מחייבת תנאים מאושרים, החלטת חיתום מתאימה, אמצעי תשלום מדומה ותנאי גבייה לפי גרסת המוצר. `ACTIVE ↔ SUSPENDED`; ביטול או סיום שומרים את התקופות והיסטוריית הכיסוי. חידוש יוצר תקופה חדשה והצעה חדשה.

תביעה: `DRAFT → SUBMITTED → VALIDATING → IN_REVIEW → APPROVED | PARTIALLY_APPROVED | REJECTED | NEEDS_INFORMATION`. השלמה חוזרת לבדיקה. הוראת תשלום נפרדת מהחלטת התביעה. `PAID` מתקבל רק לאחר ביצוע מדומה. פתיחה מחדש או ערעור יוצרים סבב החלטה חדש; לעולם אין למחוק החלטה קודמת.

הוראת תשלום: `PENDING_APPROVAL → APPROVED → EXECUTED`; ניתן לבטל לפני ביצוע. לאחר ביצוע נדרשת תנועת היפוך מאושרת, לא שינוי שדה סטטוס בלבד.

בכל פקודת מעבר: הרשאה, בדיקת מצב קודם, גרסה צפויה, סיבה כשהיא נדרשת, טרנזקציה, ביקורת ותוצאה מפורשת. API מחזיר 409 למעבר לא תקף או גרסה מיושנת, 403 להרשאה חסרה ו־422 לנתונים שאינם עומדים בתנאים.

## מנועים וכללי חישוב

פרמיה: בסיס בגרסת המוצר + תוספות מפורשות − הנחות מפורשות. לכל רכיב נשמרים מקור הכלל, בסיס ותוצאת עיגול. אין hardcode של תנאי ביטוח ישראליים. מחיר הצעה תקף עד `expiresAt`; שינויים אחרי אישור מחייבים הצעה חדשה.

חיתום: הפעלת כללים לפי סדר עדיפות, איסוף סיבות, דרישת השלמה, תנאים והחרגות. חומרת התוצאה מכריעה: דחייה, בדיקה ידנית, השלמה, אישור מותנה, אישור. התוצאה שומרת את גרסת הכללים ואת קלט הבדיקה. החלטה ידנית מעל סף הרשאה מחייבת גורם מאשר אחר.

תביעה: בדיקת תקופה במועד האירוע, קטגוריית כיסוי, אכשרה וחרגות; עלות זכאית אינה עולה על העלות הנתבעת. סדר חישוב ההשתתפות וההחזר מוגדר בגרסת המוצר. יש לתמוך בהשתתפות קבועה/אחוזית ובתקרה לכל אירוע/שורה/שנה. אין להחיל השתתפות של אירוע פעם נוספת בכל שורה. מנוע מחזיר פירוט סכומים וסיבות לשורה וגם לתביעה כולה.

יתרה זמינה = תקרה − שולם נטו − מאושר שלא שולם − שריון בדיקה פעיל. קטגוריות הסכום נפרדות. מעבר שריון בדיקה לאישור אינו יוצר שריון נוסף. תשלום מעביר מאושר לשולם באותה טרנזקציה. ביטול או תיקון משחררים רק את סכום האירוע הרלוונטי.

ביטול: חישוב חיובים עד המועד, תשלומים שהוקצו, זיכוי לפי כלל גרסה, חוב והחזר. החזר משויך למקור כספי, ואינו עולה על תשלומים זמינים להחזר. אירועי תביעה לפני הביטול עדיין נבדקים לפי תנאי הכיסוי המקוריים.

שינוי מסלול: בדיקת זכאות וחיתום מחדש לפי הצורך, חישוב דלתא לפרמיה, גרסה חדשה ומועד תחולה. אין לשנות snapshot של התקופה המקורית. שינוי רטרואקטיבי דורש הרשאה מיוחדת וסיבה.

## עקביות, מקביליות ומניעת כפל

אישור תביעה נועל חשבונות שנתיים ותקרות משנה בסדר מזהים עקבי (`SELECT ... FOR UPDATE`). חישוב מול יתרה עדכנית, כתיבת החלטה, שריון, הוראת תשלום, אירוע ביקורת ו־outbox באותה טרנזקציה. רמת SERIALIZABLE עם retry מוגבל לשגיאות serialization; אין retry אוטומטי לכשל עסקי.

`Idempotency-Key` נדרש להפקה, אישור, גבייה, תשלום, החזר וביטול. רשומה ייחודית לפי משתמש/פעולה/מפתח שומרת hash בקשה ותוצאה. שימוש באותו מפתח עם גוף שונה נכשל. constraint ייחודי מונע שני ביצועים לאותה הוראה, בנוסף לנעילה.

מסמך מיוצר מאירוע outbox לאחר commit, לא בתוך טרנזקציה ארוכה. כשל PDF אינו מבטל החלטה פיננסית: המסמך מסומן FAILED עם retry ופעולה מורשית. מפתח מסמך ייחודי כולל ישות, סוג וגרסת החלטה; worker חוזר אינו יוצר כפילות.

## REST והרשאות

כל הנתיבים תחת `/api/v1`. פעולות עסקיות מפורשות, לא שינוי חופשי של סטטוס:

- `/auth/login`, `/auth/logout`, `/auth/session`: session מאובטח, cookie HttpOnly, SameSite ו־CSRF לפעולות משנות.
- `/customers`, `/customers/:id/workspace`, `/customers/:id/pets`: חיפוש מדורג ותיק לקוח מאוחד.
- `/products/:id/versions`, `/product-versions/:id/publish`: טיוטה ופרסום מותנים בוולידציה.
- `/applications`, `/:id/quote`, `/:id/submit`, `/underwriting-cases/:id/decisions`.
- `/policies/:id/activate`, `/suspend`, `/reinstate`, `/endorsements`, `/cancellation-preview`, `/cancel`, `/renewal-quotes`.
- `/claims`, `/claims/:id/lines`, `/submit`, `/assess`, `/decisions`, `/appeals`, `/reopen`.
- `/payment-orders/:id/approve`, `/execute-simulated`, `/reverse`; `/charges/:id/collections-simulated`.
- `/documents/:id/preview`, `/pdf`, `/sign-simulated`; `/service-cases`, `/tasks`, `/reports`, `/audit-events`.

ב־OpenAPI: DTOs, pagination, מסננים, ערכי enum, שגיאות, idempotency ו־expectedVersion. כסף ב־API מוצג כמספר אגורות עשרוני בפורמט מחרוזת למניעת overflow. pagination עם cursor וסדר יציב; הרשאות גם ברמת נתון וגם ברמת פעולה.

הרשאות דוגמה: `customer.read/write`, `policy.issue/cancel/backdate`, `underwriting.decide`, `claim.assess/approve/approve_above_limit`, `payment.approve/execute/reverse`, `document.generate`, `audit.read`, `employee.manage`. אין הרשאת מנהל אוטומטית דרך בחירת תפקיד בממשק. ספים והפרדת יוזם/מאשר מנוהלים בשרת.

סיסמאות עם Argon2id, rate limiting להתחברות, session revocation ו־audit לניסיונות רגישים. סודות במשתני סביבה בלבד. מנהל ראשון נוצר רק עם סיסמת פיתוח שמספק המפעיל; אין סיסמה קבועה בקוד. אין פרטי אשראי אמיתיים.

## ממשק ומסמכים

תיק לקוח הוא סביבת העבודה המרכזית: סקירה, בעלי חיים, פוליסות, כיסויים, תביעות, תשלומים, מסמכים, פניות, משימות והיסטוריה. כל טאב משתמש ב־API ובמצבים מהשרת. טפסים רב־שלביים שומרים טיוטה. פעולה מוצגת רק לפי יכולת, אך שרת תמיד בודק מחדש. אישור מציג חישוב ותוצאה צפויה לפני ביצוע.

PDF מתבניות HTML ב־RTL באמצעות Chromium ו־Playwright, עם גופן עברי מקומי ורישיון מתועד. readiness דורש אימות טקסט עברי, pagination והורדה; קובץ PDF שנוצר בלבד אינו הוכחת תצוגה תקינה. החתימה המדומה מציגה במפורש את מגבלתה.

## תוכנית מימוש וקריטריוני יציאה

1. תשתית: monorepo, PostgreSQL, מיגרציות, health/readiness, התחברות, הרשאות, ביקורת, OpenAPI ו־RTL. יציאה: login אמיתי, 401/403, persistence אחרי restart ובדיקת rollback.
2. לקוחות/חיות/מוצרים/פוליסות/חיתום: מסלול מלא מטיוטה להפעלה; גרסאות מוצר immutable; מניעת כיסוי כפול. יציאה: יצירת לקוח וחיה, הצעה, החלטה והפעלה דרך UI ו־API.
3. תביעות: שורות, חישובים, השלמות, החלטות ויתרות. יציאה: אישור חלקי, אכשרה, החרגה, תקרה ושתי תביעות מקבילות שלא חורגות מהיתרה.
4. כספים ומסמכים: הפרדת חיוב/גבייה/זיכוי/הוראה/ביצוע; PDF עברי. יציאה: ביצוע כפול נבלם, rollback אינו משאיר חצי תנועה, כשל worker ניתן לשחזור.
5. שינויים וביטולים: גרסאות, החזרים וחידוש. יציאה: כיסוי היסטורי נשמר ושינויים מחושבים בהתאם למועד.
6. שירות ודוחות: תורים, משימות, היסטוריה ונתונים מצטברים. יציאה: כל נתון בדוח ניתן לשחזור מפעולות וספר החשבונות.
7. אינטגרציה: Playwright לפי תפקיד, מקביליות, מסמכים והתקנת Windows באמצעות Docker Compose.

Seed חוזר אינו מוחק מידע משתמש: 100 לקוחות, 140 חיות, 120 פוליסות ו־200 תביעות עם מזהים דטרמיניסטיים. התרחישים נוצרים דרך שירותי domain או builder ששומר את אותם invariants. מצבים כספיים נגזרים מאירועים תואמים, לא מספרים אקראיים לא קשורים.

המימוש התקדם ממאגר ריק למסלול ליבה עובד. ראו [מצב המימוש](implementation-status.md) לפירוט הבדיקות והפערים. מסמך זה מתאר גם יכולות מתוכננות שטרם נכתבו; אין להסיק מהופעת ישות או נתיב בתכנון שהם קיימים בקוד. ה־ORM בפועל הוא Prisma 7 עם מנוע JavaScript ומתאם PostgreSQL. הוראות ההפעלה המעודכנות נמצאות ב־README.
